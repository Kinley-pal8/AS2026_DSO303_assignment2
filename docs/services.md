# Service documentation

Every service in the design, why it beats the obvious alternative for this workload, how it is configured (all in Terraform under [`infra/`](../infra)), and what it connects to.

## Edge and frontend

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon Route 53** | DNS for `exams.<uni>.edu` | Alias records to CloudFront are free and resolve at the apex; a registrar's DNS can't alias to CloudFront and has no health-aware routing | Optional (`domain_name`, `hosted_zone_id`); A + AAAA alias to the distribution; ACM DNS-validation records | CloudFront, ACM |
| **AWS Certificate Manager** | TLS certificate for the custom domain | Free, auto-renewing; vs buying and manually rotating a certificate | DNS validated, issued in **us-east-1** (CloudFront requirement), `TLSv1.2_2021` minimum | CloudFront, Route 53 |
| **Amazon CloudFront** | Single HTTPS entry point: `/` → static SPA, `/api/*` → API | Serves 8,000 users from edge caches; one origin so no CORS; HTTP/3; vs exposing S3 website hosting (HTTP only, public bucket) or an ALB (pays per hour, no edge cache) | `redirect-to-https`; `CachingOptimized` for static, `CachingDisabled` + `AllViewerExceptHostHeader` for `/api/*`; `SecurityHeadersPolicy` (HSTS etc.); adds secret `X-Origin-Verify` header to API calls; `PriceClass_200` (includes India/Asia) | WAF, S3 web bucket (OAC), API Gateway, Route 53, ACM |
| **AWS WAF** | Layer-7 protection in front of everything | Managed rule groups maintained by AWS vs writing our own filters in code; blocks bad traffic before it costs Lambda time | Scope `CLOUDFRONT`; AWS Common (body-size rule set to *count* for large exam papers), Known Bad Inputs, IP Reputation; per-IP rate limit **20,000 / 5 min** (high on purpose: a whole campus may share one NAT IP) | CloudFront, CloudWatch metrics |
| **Amazon S3 (web bucket)** | Hosts `index.html`, `app.js`, `styles.css`, `config.js` | Static SPA needs no servers; vs EC2/Amplify hosting that costs more and adds patching | Private, Block Public Access on, readable **only** by this distribution via Origin Access Control; SSE-S3; `no-cache` on HTML/config, files uploaded by Terraform | CloudFront |

## Identity and API

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon Cognito User Pool** | Sign-in and roles (students / tutors / admins) | Managed OAuth2/OIDC with hosted login, MFA and password policy; vs building password storage ourselves or running Keycloak on EC2. Can federate to the university's Microsoft Entra ID later via SAML | Email as username; **admin-create-only** (no self sign-up); 12-char password policy; optional TOTP MFA; groups `admins`(1) `tutors`(2) `students`(3); public SPA client with **authorization code + PKCE**, no secret; ID/access tokens 60 min, refresh 12 h; token revocation on | SPA, API Gateway JWT authorizer, Lambda `api` (admin user management) |
| **Amazon API Gateway (HTTP API)** | Authenticated REST entry point for `/api/*` | HTTP API is ~70 % cheaper and lower-latency than REST API and has a native JWT authorizer, so Cognito tokens are checked before any Lambda runs; vs an ALB that can't validate JWTs per route as simply | Route `ANY /api/{proxy+}` with JWT authorizer (issuer = user pool, audience = SPA client); unauthenticated `GET /api/health`; stage throttling **1,000 rps / 2,000 burst**; JSON access logs; detailed metrics | CloudFront, Cognito, Lambda `api` alias `live`, CloudWatch |
| **AWS Lambda – `api`** | All business logic: exams, autosave, results, upload URLs, admin | Scales from 0 to thousands of concurrent requests in seconds and costs nothing between exam periods; vs EC2/ECS Auto Scaling that needs warm capacity and minutes to scale for a 5-minute spike | Python 3.13, **arm64** (cheaper), 512 MB, 15 s timeout; in **both private app subnets**; alias `live` with optional **provisioned concurrency** for exam week; X-Ray active; least-privilege role; rejects requests without the CloudFront origin header | API Gateway, RDS Proxy, DynamoDB, S3, SQS, Cognito |

## Data

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon RDS for PostgreSQL (Multi-AZ)** | System of record: exams, results, assignments, submissions | Relational data with joins and transactional "release results"; Multi-AZ gives synchronous standby + automatic failover (RPO 0 for AZ loss); vs self-managed PostgreSQL on EC2 (we'd own replication, backups, patching) or Aurora (higher minimum cost at this size) | PostgreSQL 16, `db.t4g.micro` (scale up for exams), **`multi_az = true`**, private **data subnets only**, `publicly_accessible = false`; gp3 20→100 GB autoscaling; KMS encrypted; `rds.force_ssl = 1`; 7-day PITR backups; logs to CloudWatch; master password managed in Secrets Manager | RDS Proxy, Secrets Manager, KMS, AWS Backup, CloudWatch |
| **Amazon RDS Proxy** | Connection pool between Lambda and PostgreSQL | Thousands of short-lived Lambda invocations would exhaust `max_connections`; the proxy multiplexes them and shortens failover; vs PgBouncer on EC2 we'd have to run and make HA ourselves | `require_tls`; **IAM authentication required** (Lambdas use 15-min tokens, no password in code); reads DB secret from Secrets Manager; 90 % max connections, 120 s borrow timeout; endpoints in both data subnets | Lambda `api`/`marker`/`uploads`, RDS, Secrets Manager |
| **Amazon DynamoDB (`attempts`)** | Live exam attempts and 30-second autosaves | ~100 small writes/s at peak with single-key access is ideal for DynamoDB: no connections, single-digit-ms, on-demand scaling; vs writing autosaves to RDS (connection and IOPS pressure at the worst moment) or ElastiCache (not durable) | **On-demand**; key `attempt_id = examId#studentSub` (no hot partition); conditional writes enforce deadline server-side; sparse GSI `open-by-deadline` (KEYS_ONLY) for the sweeper; **PITR on** (restore to any second, RPO ≈ seconds); KMS CMK | Lambda `api`, `marker`, `sweeper`, gateway endpoint, AWS Backup |
| **Amazon S3 (uploads bucket)** | Assignment files (PDF/ZIP ≤ 50 MB) | 11 nines durability, unlimited size, cheaper than EBS/EFS; **presigned POST** keeps 50 MB bodies off API Gateway (10 MB limit) and Lambda (6 MB); lifecycle tiers make 5-year retention cheap | Block Public Access; **SSE-KMS** + bucket key; versioning; **lifecycle**: Standard → Standard-IA 30 d → Glacier IR 180 d → Deep Archive 365 d → **expire 1,825 d (5 y)**; old versions expire 30 d; abort incomplete multipart 7 d; deny non-TLS; CORS only from the app origin; `ObjectCreated` events → SQS | Browser (presigned), Lambda `api`/`uploads`, SQS, KMS, gateway endpoint |
| **AWS Backup** | Long-term database backups for the 5-year retention requirement | One policy across RDS and DynamoDB with a KMS-encrypted vault; vs RDS automated backups alone (max 35 days) | Daily rule kept 35 days; **monthly rule kept 1,825 days**; selection = RDS instance + DynamoDB table | RDS, DynamoDB, KMS |

## Asynchronous processing

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon SQS** (`marking`, `uploads`, `notifications` + DLQs) | Buffers work so the request path stays fast; smooths the end-of-exam surge | Durable, at-least-once, scales with no setup; with Lambda event source mappings we can **cap concurrency** to protect the DB; vs SNS (no buffering/back-pressure) or Kinesis (ordered streams we don't need, shard management) | SSE on; visibility 180 s (6× function timeout); **DLQ after 5 receives**, DLQ kept 14 days; batch 10, 2 s window, partial batch failure reporting; max concurrency marking 20 / uploads 10 / notifications 5; uploads queue policy only accepts this bucket | Lambda `api`, `sweeper`, `uploads`, `marker`, `notifier`; S3 events |
| **AWS Lambda – `marker`** | Auto-marks MCQs, writes results | Event-driven, scales with queue depth, idempotent upsert; vs marking inline during submit (slow, fails the student's request if the DB is busy) | 256 MB, 30 s, in VPC; reads attempt (consistent read) → `INSERT … ON CONFLICT DO UPDATE WHERE NOT released` | SQS marking, DynamoDB, RDS Proxy |
| **AWS Lambda – `uploads`** | Validates uploaded files, records submission, triggers e-mails | Runs only when files arrive; vs polling S3 from a server | Checks size ≤ 50 MB and magic bytes (`%PDF`, `PK`); tags rejects; `ON CONFLICT (s3_key) DO NOTHING` for duplicate events; computes `late` | SQS uploads, S3, RDS Proxy, SQS notifications |
| **AWS Lambda – `notifier`** | Sends e-mails | Separating e-mail lets SES throttling/outages retry without affecting marking or uploads | Not in VPC (needs only SES); permanent SES errors logged, transient retried → DLQ | SQS notifications, SES |
| **AWS Lambda – `sweeper`** + **Amazon EventBridge** | Auto-submits attempts whose time ran out (student closed the laptop) | Scheduled serverless job; vs cron on an EC2 instance (a single point of failure) | `rate(1 minute)`; queries sparse GSI `open_status = OPEN AND deadline < now − 60 s`; sets SUBMITTED, queues marking | EventBridge, DynamoDB, SQS marking |
| **Amazon SES** | Result-release, submission and receipt e-mails | Pay-per-email, high deliverability, DKIM support; vs SNS e-mail (no custom content/sender, recipients must confirm a subscription) or running our own SMTP | Verified sender identity (`ses_sender_email`); IAM restricted to `ses:FromAddress`; production needs sandbox exit + a verified university domain with DKIM | Lambda `notifier` |

## Network

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon VPC** | Private network isolating compute and data | Needed so the database has no public path; tiers separated by subnet and security group | `10.20.0.0/16`; **2 AZs × 3 tiers**: public `10.20.0-1.0/24`, private app `10.20.10-11.0/24`, private data `10.20.20-21.0/24` (no internet route); flow logs (REJECT) to CloudWatch | All VPC resources |
| **Internet Gateway + NAT Gateways** | Outbound internet for private Lambdas (KMS, SQS, Cognito, X-Ray APIs) | Managed, HA within an AZ; **one per AZ** so losing an AZ doesn't cut the other's egress; vs NAT instances we'd patch and fail over ourselves | `nat_gateway_per_az = true` (set false for cheap testing); per-AZ app route tables | Public/app subnets |
| **VPC Gateway Endpoints (S3, DynamoDB)** | Private, free path to S3 and DynamoDB | Keeps the busiest traffic (autosave writes, file reads) off NAT (saves $/GB) and off the internet | Attached to both app route tables | Lambda, S3, DynamoDB |
| **Security Groups** | Stateful firewall chain | SG-to-SG references instead of CIDRs mean only the right tier can talk | `lambda` → `proxy:5432` → `db:5432`; DB accepts **only** the proxy SG | Lambda, RDS Proxy, RDS |

## Security, monitoring, delivery

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **AWS KMS** | Encryption at rest | Customer-managed key gives audit (CloudTrail) and revocation; vs AWS-owned keys with no control | One CMK, **annual rotation**, alias `alias/uniexam-prod`; used by RDS, DynamoDB, S3 uploads, DB secret, backup vault | RDS, DynamoDB, S3, Secrets Manager, Backup, Lambda roles |
| **AWS Secrets Manager** | Holds the database master password | RDS-managed secret is generated and **rotated automatically**, never seen by humans or code; vs a password in tfvars/env vars | `manage_master_user_password = true`, KMS-encrypted; only the RDS Proxy role can read it | RDS, RDS Proxy |
| **AWS IAM** | Least-privilege access | One role per Lambda with only the actions/resources it needs (e.g. `notifier` can only `ses:SendEmail` from the sender address); GitHub uses **OIDC** (no stored keys) | Per-function inline policies in `compute.tf`; `rds-db:connect` scoped to proxy + user | All services |
| **Amazon CloudWatch** (+ X-Ray) | Logs, metrics, alarms, dashboard, traces | Native to every service used; vs a 3rd-party APM needing agents | 30-day log retention; alarms: Lambda errors, API 5xx, API p95 > 1 s, DLQ not empty, marking backlog > 10 min, RDS CPU/storage, DynamoDB throttles; dashboard `uniexam-prod`; X-Ray tracing on all Lambdas | All services, SNS |
| **Amazon SNS** | Alarm fan-out | Simple e-mail/SMS/chat fan-out for alarms | Topic `uniexam-prod-alarms`, e-mail subscription `alarm_email` | CloudWatch alarms |
| **Terraform** + **S3 state** | Infrastructure as code | Whole stack reproducible from git; plan shows changes before apply; vs console clicks (not repeatable) or CloudFormation (more verbose; Terraform also manages us-east-1 WAF in one run) | AWS provider 6.x; remote state in versioned, encrypted S3 with native lockfile; `protect_data` toggle for production deletion protection | All resources |
| **GitHub Actions** | CI/CD: test → validate → deploy on push to `main` | Lives with the code, free for this scale; vs CodePipeline (more setup, separate console) | PRs: pytest + `terraform fmt/validate`; `main`: OIDC role → build Lambda zip → `terraform apply` → CloudFront invalidation → `/api/health` smoke test; `production` environment can require approval | AWS (OIDC role), S3 state |
